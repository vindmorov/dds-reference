# План реализации DDS Beta Flow

## Принцип реализации

Работа выполняется по вертикальным срезам. После каждого среза проверяется основной пользовательский сценарий. Текущий экран DDS сохраняется как рабочая аналитическая часть и подключается после завершения импорта.

## Фаза 0. Техническая подготовка

1. Зафиксировать текущую версию DDS и проверить сборку.
2. Разделить приложение на onboarding, импорт и аналитическую часть.
3. Добавить единый объект состояния пользователя: текущий этап, файл, операции, категории, прогресс проверки и неразобранные операции.
4. Определить адаптивные правила для desktop, tablet и mobile.

Проверка: существующий DDS открывается без импорта в режиме демо/пустого состояния.

## Фаза 1. Лендинг и аккаунт

1. Создать лендинг с объяснением трёх ценностей DDS.
2. Добавить CTA «Попробовать DDS».
3. Создать экран регистрации.
4. Добавить валидацию обязательных полей и состояния ошибки.
5. Сохранить тестового пользователя в mock-хранилище.

Проверка: пользователь проходит лендинг и регистрацию, после чего попадает на загрузку.

## Фаза 2. Загрузка выписки

1. Создать экран загрузки Excel/CSV.
2. Добавить ссылку на скачивание шаблона.
3. Проверять расширение, размер, наличие строк и обязательных полей.
4. Поддержать сопоставление колонок произвольного файла.
5. Показать понятные сообщения об ошибках и возможность повторной загрузки.

Проверка: корректный шаблон загружается, неправильный файл даёт объяснимую ошибку, данные не теряются при повторной попытке.

## Фаза 3. Контекст бизнеса и импорт

1. Добавить вопросы о бизнесе: вид деятельности, другие банки, юридические лица и период.
2. Реализовать преобразование строк файла в `Transaction`.
3. Определить поток по знаку суммы и предложить направление/категорию.
4. Рассчитать `confidence` для каждой операции.
5. Показать прогресс обработки и предварительную сводку.

Проверка: из тестового файла формируется набор операций с датами, суммами, потоками, категориями и уверенностью.

## Фаза 4. Проверка операций

1. Создать экран итогов распределения.
2. Реализовать пошаговую проверку сомнительных операций.
3. Добавить подтверждение, смену категории, применение к похожим операциям и пропуск.
4. Добавить таблицу массового редактирования.
5. Сохранять прогресс после каждого действия.
6. Разрешить перейти в DDS с неразобранными операциями.

Проверка: пользователь может разобрать часть операций, закрыть приложение и продолжить с того же места.

## Фаза 5. Настройка категорий

1. Создать универсальный экран потоков «Поступления» и «Списания».
2. Отобразить категории, направления, суммы и количество операций.
3. Добавить создание, переименование, перемещение, объединение и скрытие категории.
4. Применять изменения категорий к связанным операциям.
5. Показать итог готовности данных.

Проверка: после изменения категории суммы и принадлежность операций в DDS обновляются согласованно.

## Фаза 6. Подключение к DDS

1. Заменить статический источник `financeRows` адаптером аналитических данных.
2. Сохранить иерархию: направление → поток → категория.
3. Сохранить простой и табличный режимы.
4. Подключить динамику по месяцам к импортированным операциям.
5. Генерировать инсайты на основе изменений и порогов внимания.
6. Связать инсайт с категориями и операциями.

Проверка: пользователь видит свои направления, категории, месячную динамику и может открыть инсайт до конкретной категории.

## Фаза 7. Действия и обратная связь

1. Добавить действия из инсайта: проверить операции, изменить план, добавить статью, отложить и отметить решённым.
2. Сохранять статус инсайта.
3. Добавить опрос после первого анализа.
4. Сохранить ответы в mock-хранилище для бета-теста.

Проверка: пользователь открывает инсайт, просматривает динамику, выполняет действие и отправляет опрос.

## Фаза 8. Сохранение и повторный вход

1. Сохранять данные аккаунта, импорт, категории и прогресс проверки.
2. Восстанавливать последний незавершённый этап.
3. Показывать предупреждение о неразобранных операциях.
4. Обеспечить экспорт/очистку тестовых данных для бета-тестирования.

Проверка: после перезагрузки пользователь возвращается к своему проекту без потери состояния.

## Порядок проверки

- unit-проверки парсинга, нормализации суммы, определения потока и расчёта уверенности;
- component-проверки состояний загрузки, ошибок, проверки и категорий;
- сценарная проверка полного happy path;
- проверка неполного файла и пропуска операций;
- responsive-проверка 375px, 1024px и desktop;
- production build и проверка архива для April.

## Что не входит в первый релиз

- банковские интеграции;
- реальная серверная авторизация;
- ML-классификация без подтверждения пользователя;
- сложные роли и совместная работа;
- полноценная финансовая отчётность.
